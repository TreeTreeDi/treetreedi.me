## 1. 背景与痛点：为什么必须接管记忆系统？

每一次打开 Claude Code，面对的都是一个全新的上下文窗口。

在日常开发中，我们经常遇到这样的崩溃场景：花了一个小时和 Claude 一起排查了一个深水区的 Bug，但在 Session 被 Compact（压缩）之后，这段宝贵的排错过程可能只被浓缩成了一句冷冰冰的 "fixed XX issue"。下次打开新对话时，Claude 对你的项目结构、技术栈、踩过的坑再次一无所知。

这就导致了一个极具摩擦力的开发日常——你每次开始工作都要向它重新解释："这个项目必须用 pnpm"、"测试前需要启动本地 Redis"、"组件传参严禁使用 any 类型"......

**这些反复的解释是纯粹的摩擦，在高效的工程链路中不应该存在。**

为了解决这个问题，Claude Code 提供了两种方向相反但高度互补的解法：

1. **静态声明 (`CLAUDE.md`)**：由开发者主动编写，明确告知 Claude 项目的规范与红线。

2. **动态捕获 (Auto Memory)**：由 Claude 在工作流中自己给自己记的“笔记”，沉淀实践经验。

理解这两套系统的加载规则与运作逻辑，是让 Claude 从“日抛型助手”进化为“懂你工作流的工程老兵”的关键所在。

## 2. 核心架构：规范契约 vs 经验日志

在系统设计上，这两种记忆机制承担着完全不同的工程职责。

`CLAUDE.md` 系列是你维护的，内容是**规范性**的。这些是稳定的、可以被团队共享的约定，适合通过 Git 追踪和版本化。 Auto Memory 是 Claude 自己维护的，内容是**经验性**的。这些是从实践中模糊积累的，不适合手动整理，让 AI 自己记录更符合自然直觉。

| 维度         | CLAUDE.md (静态声明)           | Auto Memory (动态捕获)                     |
| ------------ | ------------------------------ | ------------------------------------------ |
| **谁来写**   | 开发者                         | Claude 引擎                                |
| **写什么**   | 规范、约定、核心指令、架构说明 | 调试经验、代码模式、个人习惯与偏好         |
| **更新时机** | 人工评估并修改                 | AI 运行时自动判断 / 用户显式指令           |
| **团队共享** | **可以**（通过 Git 提交）      | **不可以**（存储于本地沙盒，属于私有记忆） |
| **控制精度** | 绝对精准，严格遵循             | 模糊累积，依赖大模型检索                   |

这两套机制在每次 Session 开始时并行加载，共同构成 Claude 对当前项目的全盘背景知识。

## 3. 记忆文件放在哪里：六个作用域层级

`CLAUDE.md` 体系的配置文件按作用域由广到窄划分为六种位置。**优先级规则是：越具体的配置优先级越高。** 项目级的约定会覆盖用户级，用户级会覆盖组织级。

1. **组织级**：由 IT 部门或 DevOps 统一部署，覆盖组织内所有用户所有项目。适合公司层面的编码规范、安全策略。
   - _macOS_: `/Library/Application Support/ClaudeCode/CLAUDE.md`

   - _Linux_: `/etc/claude-code/CLAUDE.md`

   - _Windows_: `C:\Program Files\ClaudeCode\CLAUDE.md`

2. **用户级**：你个人的偏好设置，覆盖你在所有项目中的行为（如喜欢的代码风格、常用 CLI 工具）。`~/.claude/CLAUDE.md`
3. **用户规则**：用户级配置的模块化版本，按主题拆分成多个文件（如 `preferences.md`, `workflows.md`）。`~/.claude/rules/*.md`

4. **项目级（最常用）**：当前项目的团队共享约定。通过 Git 追踪，团队成员都会加载相同的规范。`./CLAUDE.md` 或 `./.claude/CLAUDE.md`

5. **项目规则**：项目级记忆的模块化版本。支持按文件路径精确过滤加载（后文详述）。`./.claude/rules/*.md`

6. **本地项目级**：只对你本人生效的私有配置（例如你个人的沙盒 URL、私有数据库账号）。`./CLAUDE.local.md`（注：Claude Code 会自动尝试将此文件加入 `.gitignore`）。

## 4. 加载机制：基于目录树的冒泡与懒加载

Claude Code 的记忆加载有一个极其核心的设计原则：**从当前工作目录（CWD）出发。**

### 4.1 向上递归加载（启动时全量挂载）

启动时，Claude Code 从 CWD 开始，向上递归遍历父目录，一直到系统根目录（不含 `/`），把沿途所有符合格式的 `CLAUDE.md` 及其变体全量加载进上下文。

假设你在 `/Users/you/code/myapp/src/api` 下启动 Claude Code，它会依次检查并加载：

1. `/Users/you/code/myapp/src/api/CLAUDE.md`

2. `/Users/you/code/myapp/src/CLAUDE.md`

3. `/Users/you/code/myapp/CLAUDE.md`

4. `/Users/you/code/CLAUDE.md`

5. 全局配置如 `~/.claude/CLAUDE.md`

_架构思考：这个设计对大型 Monorepo 极具价值。可以在根目录写通用的 DevOps 规范，在 `frontend/` 子目录写前端专属规范。在哪个目录下启动，就自动获得对应层级的全部上下文。_

### 4.2 子目录的按需加载（懒加载策略）

工作目录**下方**的子目录里如果有 `CLAUDE.md`，行为则完全不同：**Claude Code 不会在启动时主动加载它们。**

只有当 Claude 在会话中实际读取了那个子目录里的文件，才会触发加载对应的 `CLAUDE.md`。 _底层思考：理由很直接。一个大型项目可能有几十个微服务子模块，每个都有自己的规范。如果全部在启动时加载，上下文窗口会立刻被无效信息撑满。懒加载保证了只有“真正在处理的模块”，其规范才会进入上下文。_

在 claude mem 这个开源项目中就用到了这样的一个观点，他会在每一个修改的文件同一级目录里创建一个记忆文件，来提示这个文件在什么时候经过了哪些更改，来方便AI进行读取， 就符合了 Claude 会话读取的策略。

## 5. Auto Memory：AI 视角的工程笔记

Auto Memory 是 2.1.x 版本引入的核心功能。

### 5.1 存储寻址机制

每个项目都有独立隔离的 Auto Memory 目录，位置在： `~/.claude/projects/<project-hash>/memory/`

- **哈希逻辑**：`<project-hash>` 是将 Git 仓库根目录绝对路径中的 `/` 替换成 `-` 生成的。例如 `/Users/you/code/myapp` 变成 `-Users-you-code-myapp`。

- **边界情况梳理**：
  - 同一个 Git repo 下的所有子目录，无论你在哪工作，均**共用同一份** Auto Memory。

  - **Git Worktree 各自有独立的目录**，不互通。

  - 若 CWD 不在 Git 仓库内，直接用当前工作目录路径作为标识。

### 5.2 MEMORY.md 的 200 行调度法则

记忆目录并非单一文件，而是由 Claude 自主维护的文件树：

```
memory/
├── MEMORY.md          # 入口文件，索引 + 摘要
├── debugging.md       # 专项：调试经验记录
└── api-conventions.md # 专项：API 约定
```

`MEMORY.md` 是主索引。每次 Session 启动时，**系统只会将其前 200 行自动注入系统提示词**。Claude 被明确设定为必须保持此文件精简。 当积累的内容逼近上限，Claude 会自动触发重构，将长文本拆分转移到 `debugging.md` 等专项文件中，并在主索引中留下文件路径和短摘要。需要深挖时，Claude 会调用标准文件工具去读取专项文件。

### 5.3 写入时机与人工干预

Claude 在工作时会自行判断并静默写入（例如发现重复代码模式、解决复杂链路 Bug 后）。但这同样支持自然语言的**显式强干预**：

> “记住我们这个项目用 pnpm，不是 npm” “把这个记到记忆里：API 测试前需要先启动本地 Redis” “下次记得：这个组件不能直接修改 props，必须通过回调”

此外，随时可在对话中输入 `/memory` 命令，呼出文件选择器手动删改这些记忆文件。

## 6. 高阶约束：模块化规则与过滤

当项目的 `CLAUDE.md` 越来越长时，团队维护成本会剧增，不同主题混杂极易引发 Git 冲突。官方的终极解法是 `.claude/rules/`。

### 6.1 @ 引用语法

`CLAUDE.md` 支持直接使用 `@path` 引入其他文件内容，避免信息堆砌（最高递归 5 层）：

```
项目概述见 @README.md
# 开发规范
- Git 工作流详见 @docs/git-instructions.md
- API 设计规范 @docs/api-design.md
```

_(注：首次跨域引用如 `~/.claude/` 路径时，系统会弹出授权对话框防范越权读取。)_

### 6.2 YAML 路径过滤 (Glob Filtering) - 核心特性

`.claude/rules/*.md` 目录下所有的文件都会被发现，但其最具价值的特性是支持用 YAML Frontmatter 限定加载范围。

**只有当 Claude 在处理匹配该路径的文件时，这个规则文件才会进入上下文：**

```
---
paths:
  - "src/api/**/*.ts"
  - "lib/**/*.ts"
---
# API 开发规范
- 所有端点必须包含输入验证，严禁直接信任客户端数据。
- 错误响应必须遵循统一格式：`{ error: string, code: string }`
```

_底层思考：路径过滤的终极目的是“隔离噪音”。处理前端组件时不需要加载数据库操作规范，按需匹配让每一次的 System Prompt 都保持最高的纯净度与信息密度。_

## 7. 架构思考：记忆系统的生命周期与演进复盘

这套系统的长期使用，必须建立在一种健康的“知识演进路径”上。如果长期不整理，会出现两大灾难：

1. **记忆污染**：Auto Memory 积累了大量过期设定。**在 AI 辅助编程中，过期的记忆比没有记忆更危险**，因为 Claude 会把它当成不可动摇的当前事实，从而引发顽固的幻觉（Hallucination）。

2. **知识孤岛**：有巨大价值的工程经验只存在于你本地的 Auto Memory 里，团队其他人根本无从知晓。

**最佳实践：定期梳理与“经验上卷”**

我们需要将 Auto Memory 视作“草稿本”，将 `CLAUDE.md` 视作“法典”。它们的演化路径应该是单向向上的：

```
实践中遇到问题，解决问题
      ↓
Auto Memory 自动捕获并记录（本地私有，项目级粗颗粒度）
      ↓
定期复盘（执行 /memory 检视）
      ↓ 提取 / 舍弃过期废料
发现具有团队共性价值的通用规律（如环境配置陷阱、特定组件用法）
      ↓ 抽象与提炼
写入项目级的 CLAUDE.md 或 .claude/rules/*.md 中
      ↓
提交 Git，实现团队共享与版本化（知识沉淀完毕）
```

Auto Memory 是敏捷的工作日志，`CLAUDE.md` 是沉淀下来的稳定契约。两者配合，才能既记住当下瞬息万变的开发细节，又能传承长治久安的团队规范。

## 8. 附录：原生体系与第三方社区方案的对比

除了官方内置的上述两套机制，目前社区中也活跃着诸如 [claude-mem.ai](https://claude-mem.ai/ 'null') 这样的第三方开源解决方案。为了防止混淆，需明确其边界：

- **官方原生架构 (本文重点)**：基于纯文本（Markdown）、基于目录树冒泡与大模型自身的上下文窗口（200行机制）进行轻量级索引。优势是无缝集成、零依赖配置。

- **第三方扩展 (如 claude-mem)**：通常基于本地 SQLite + 向量数据库（如 Chroma），通过拦截 Claude Code 的生命周期 Hook，对海量历史对话进行向量化持久存储与语义检索。

- **选型建议**：对于常规的项目级规范同步与调试，官方的 `CLAUDE.md` + `Auto Memory` 已完全足够。如果你需要在几十个毫无关联的 Repo 之间共享某种深度的全局抽象知识库，再考虑引入重型的第三方向量记忆插件。
